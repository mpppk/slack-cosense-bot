# niki 運用規約

このリポジトリは **LLM が維持管理する個人リサーチ wiki** の規約（schema 層）の正本である。
wiki の実体は Cosense プロジェクトにあり、このリポジトリには wiki のコンテンツを置かない。

管理する Cosense プロジェクトは `projects/` 下で定義する。現時点では次の 4 つ:

- **niki-auth** — https://scrapbox.io/niki-auth — 認証認可に関するナレッジを管理するプロジェクト
- **niki-ai** — https://scrapbox.io/niki-ai — AIエージェントやLLMに関するナレッジを管理するプロジェクト
- **niki-cs** — https://scrapbox.io/niki-cs — カスタマーサポートを行うSaaSに関するナレッジを管理するプロジェクト
- **niki-tech** — https://scrapbox.io/niki-tech — 認証認可やAI以外の技術一般に関するナレッジを管理するプロジェクト

このファイル（`AGENTS.md`）は全プロジェクト共通の規約である。プロジェクト固有の事情がある場合は `projects/<name>/` 下に追記する。

元になったアイデア: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

## 0. 前提

- 用途は **リサーチ**（特定テーマを継続的に深掘りし、thesis を育てる）。
- **source は Cosense のページとして保持してもよいが必須ではない**。本文を転記した `#raw` ページとして保持することも、`🔖` bookmark として URL のみを保持することもできる。bookmark はページタイトルが URL のタイトルで、本文に URL を持つ。summary を書かない仮置きと、summary を直接書く場合の 2 通りがあり、タイトルと本文の作りは §6 識別で定める。いずれの場合も外部ストレージや git には置かない。
- wiki は LLM が書き、人間は読む。人間の仕事はソースの選定・探索・問いを立てること。
- 操作は `cosense` CLI（`@helpfeel/cosense-cli`）経由で行う。詳細は `cosense <command> --help`。
- **ページの新規作成・編集はユーザーが明示的に指示した時のみ行う。** 閲覧・調査は随時よい。
  指示はチャットだけでなく wiki 上にも書ける（§12）。

### 語彙

**構造を表す語はすべて原著（karpathy の gist）の英語をそのまま使う。** 訳さない。

型名・Infobox のキー・summary ページの節名・操作名がこれに当たる。理由は 3 つ。

1. 「出典 / 情報源 / ソース」のような**表記ゆれが原理的に起きない**。
   Cosense ではタイトルが実質的な ID なので、揺れは即座に知識の分断になる（§3）。
2. **小文字の英語＝構造、それ以外＝内容**、という視覚的な区別がページ一覧で効く。
3. どこが原著由来でどこが独自の拡張かが、名前を見れば分かる。

**すべて小文字・単数形で書く。** `Concept` や `concepts` は作らない。

wiki の内容そのもの（本文の散文、および個々の concept / person / organization ページの
タイトル）は日本語でよい。規約として英語に固定するのは、型名とキーの閉じた語彙だけである。

## 1. アーキテクチャ

karpathy の 3 層を Cosense 上に写像する。層の名前は原著のまま。

| 層 | 実体 |
|---|---|
| sources | Cosense の source ページ（`#raw` または `🔖` bookmark。詳細は §6） |
| wiki | Cosense のそれ以外の全ページ |
| schema | このリポジトリ（`AGENTS.md` が共通規約、`docs/` が操作時の手続き、`projects/` 下がプロジェクト定義） |

**`AGENTS.md` は規約、`docs/` は手続きを持つ。** 何が正しいかを定めるのが規約で、
それをどうやるかが手続きである。手続きは対応する操作を実行するときだけ読めばよいので、
常時読む `AGENTS.md` から外に出す。どこを読むかは各節が指す。

管理対象の Cosense プロジェクトは `projects/` 下のディレクトリで定義する。各 `projects/<name>/` は当該プロジェクトのローカルなメタデータや補足（`config.json` 等）を置く場所であり、wiki 本体は常に Cosense 側にある。`AGENTS.md` に書かれた規約は全プロジェクトに共通で適用し、プロジェクト固有の事情だけを `projects/<name>/` 下に追記する。

Cosense はフォルダを持たない完全にフラットな名前空間である。
**階層・分類はすべてリンクで表現する。** ディレクトリ構造を命名で模倣してはならない。

原文も同じ名前空間に置くため、source ページには **タイトル先頭の `📄` / `🔖` と本文冒頭の `#raw` / `#bookmark`**
という 2 つの目印を付ける（§6）。これが wiki 層と source 層を分ける唯一の手段である。

## 2. ページの型

すべてのページは **本文 1 行目に型を 1 つだけ**持つ。これがフォルダの代わりになる。

| 型 | 用途 | 原著での扱い |
|---|---|---|
| `#raw` | 取り込んだソースの原本。1 ソース 1 ページ。型のみハッシュタグ記法（§6） | 別レイヤー。ページ型ではない |
| `#bookmark` | URL のみを保持する source。1 ソース 1 ページ。summary を書かない場合の仮置き。型のみハッシュタグ記法（§6） | 新設。raw の軽量な代替 |
| `[summary]` | 1 ソースの要約・takeaways・引用・参照先。raw の場合は対応する `📄` ページへリンクし、bookmark の場合は `🔖` タイトルで summary 自体に URL を持つ（§6） | "summary page" |
| `[concept]` | 概念・手法・用語・アルゴリズム | "concept pages" |
| `[person]` | 著者・研究者 | "entity pages" を細分 |
| `[organization]` | 研究機関・企業 | "entity pages" を細分 |
| `[thesis]` | テーゼ・仮説。支持／反証する summary と現在の確信度を持つ | "an evolving thesis"（語のみ） |
| `[question]` | ユーザーの問いと、その回答を清書したもの | 概念はあるが型名はない |
| `[synthesis]` | 複数ソースを横断する統合・比較 | "comparisons" / "a synthesis" |
| `[idea]` | ユーザーが実現したいこと。実現を助ける／阻む summary と現在の状態を持つ（§8） | 新設 |
| `[log]` | 日付ページ | "log.md"（原著は 1 枚） |

`[thesis]` がリサーチ用途の中心である。読んだものを溜めるだけでなく、
**「現時点で何が言えるのか」を明示的なページとして持ち、summary が増えるたびに更新する。**

原著は "an evolving thesis" を wiki 全体の単一の立場として語るが、
ここでは**命題ごとに 1 ページ**とし、確信度を個別に持たせる。

### 型の使い分け

紛らわしい境界を 4 つ明示する。

**`[summary]` と `[synthesis]`** — **1 ソースで書けるなら summary、2 つ以上必要なら synthesis。**
1 本の論文の中にある比較表は、その論文の summary に属する。
複数のソースを並べて初めて言えることだけが synthesis になる。

**`[synthesis]` と `[thesis]`** — **真偽を問えるかどうか。**
`[thesis]` は命題で、`supported_by` / `refuted_by` / `confidence` を持つ
（例: 「再帰なしで長距離依存を扱える」）。
`[synthesis]` は整理で、真偽を問えない（例: 「位置エンコーディング手法の比較」）。
synthesis を書いていて「つまりこう言える」が出てきたら、それは thesis として切り出す。

**`[thesis]` と `[idea]`** — **世界について言えることか、自分がやりたいことか。**
`[thesis]` は世界についての命題で、支持／反証が集まる。
`[idea]` はユーザーの意志で、真偽を問えない代わりに実現を助けるもの／阻むものが集まる。
「X は Y で実現できる」は前者、「X を実現したい」は後者である。
1 つのアイデアから実現可能性の命題が切り出せるなら **thesis として別ページに立て、
idea の `approach` から参照する。** 意志と命題を 1 枚に混ぜると、
どちらの更新規則（`confidence` か `status` か）に従うのかが決まらなくなる。

**`takeaways` は型ではない。** summary ページの中の節名である（§7）。
1 ソースについての粒度は source（raw の全文または bookmark の URL）→ `takeaways`（箇条書き）→ `gist`（1 行）の 3 段で、
読む目的に応じて使い分ける。

### 型名と内容ページの衝突

`concept` `entity` `log` などは、リサーチ対象の用語としても現れうる
（例: 固有表現抽出の文脈での "entity"）。衝突したときは **内容ページ側の名前を具体化する**
（`entity` ではなく `固有表現` や `named entity`）。型ページの名前は動かさない。
型ページを改名すると全ページのリンクに波及するが、内容ページの改名は 1 枚で済む。

## 3. タイトル規約

Cosense ではタイトルが実質的な ID かつリンク先であり、表記ゆれが即座に知識の分断になる。

- **名詞句にする。説明文にしない。** 他ページの本文中に `[...]` の形で自然に書ける形であること。
- **表記ゆれは正式名 1 つに寄せる。** 略称・英語名・和訳は別名ページを作り、
  本文に本体への 1 行リンクだけを書く（リダイレクト代わり）。
  例: ページ `k8s` の本文は `[Kubernetes]` の 1 行のみ。
- **`/` で始めない。** `[/project/page]` は他プロジェクトへのリンク記法と衝突する。
- **プレフィックスで疑似階層を作らない。** `source/xxx`、`concept/xxx` などは禁止。型で表す。
- **summary ページのタイトルは原題そのまま。** 日付や連番のプレフィックスは付けない。
  同名が衝突する場合のみ末尾に ` (2019)` のように発行年を足す。ただし bookmark の summary は例外で、タイトル先頭に `🔖` を付け URL のタイトルをそのまま使う（§6）。
- **原文ページはタイトル先頭に `📄` を付ける。** 接頭辞による識別はこれだけが例外である。
  疑似階層ではなくレイヤーの識別子なので、上の禁止（`concept/xxx` 等）とは目的が違う。
  検索結果から原文を機械的に選り分けるために使う（§9）。
  **絵文字は 1 コードポイントのものに限る。** `🗒️` や `⚠️` のように異体字セレクタ `U+FE0F` を
  持つ絵文字は、付いたり落ちたりするとタイトル＝ID が変わりページが静かに分裂する。
  `📄` は `U+1F4C4` 単独で安全である。
- **bookmark ページはタイトル先頭に `🔖` を付ける。** 同じく source 層の識別子であり、上記と同様の例外である。`🔖` は `U+1F516` 単独で安全である。

## 4. リンク規約

Cosense の価値はリンクグラフにある。リンクの質がそのまま wiki の質になる。

- 本文に出てくる固有名詞・概念は **必ず `[ ]` で囲む。ページが存在しなくてよい。**
  未作成ページへのリンク（空リンク）は「次に書くべきページ」のキューとして機能する。
- **孤立ページを作らない。** 新規ページを作ったら、必ずどこかから被リンクを 1 本以上張る。
- **「関連ページ」節を手書きしない。** Cosense が被リンクを自動表示するため冗長であり、必ず腐る。
- **ハッシュタグ記法は `#raw` / `#bookmark` にのみ使う。** `#foo` と `[foo]` は動作が同じなので、
  それ以外はすべてリンク記法に統一して揺れをなくす。`#raw` / `#bookmark` は source ページの目印を
  本文冒頭で視認しやすくするための例外である（§6）。
- **`[summary]` `[thesis]` `[idea]` へは、その型の instance 以外からリンクしない。**
  リンクしたページが Infobox の表に捏造行として現れるため（§5）。
  他ページの本文で言及するときは平文で `summary` / `thesis` / `idea` と書く。
  クリックで辿れるようにしたいときは **外部 URL 記法**
  `[summary https://scrapbox.io/niki-auth/summary]` のように `https://scrapbox.io/<project>/summary` を使う（`<project>` は `niki-auth` / `niki-ai` / `niki-cs` / `niki-tech` のいずれかに置き換える）。
  人間にはリンクとして見えるがリンクグラフには乗らないため、表を汚さない。
- **操作ページ `[ingest]` `[query]` `[lint]` へも、指示行以外からリンクしない。**
  被リンクが未処理の指示のキューだから（§12）。導線には同じく外部 URL 記法を使う。
- **アイコン記法 `[name.icon]` はリンクグラフに乗らない。** 発言の署名にのみ使う（§12）。
- **目次ページ・index ページを作らない。** 被リンクと Infobox（§5）が自動インデックスになる。
  手書きの目次は更新漏れで必ず腐る。
- リンクは「そこから辿りたいもの」に限る。文中の全単語をリンクにしない。

## 5. Infobox（文芸的データベース）

YAML frontmatter + Dataview に相当する機能。
型定義ページ本文に `table:infobox` を宣言し、各ページに同じキーの Infobox を書くと、
**その型にリンクしている全ページの値が自動で表に集計される。**

```
cosense browseRelatedPages https://scrapbox.io/<project>/summary
```

で全 summary の一覧表が TSV で得られる。これが index.md の代替であり、手書きより常に正しい。

定義するキー:

| 型 | キー |
|---|---|
| `[summary]` | `gist` / `kind` / `author` / `published` / `ingested` / `raw` / `url` / `credibility` |
| `[thesis]` | `confidence` / `supported_by` / `refuted_by` / `reviewed` |
| `[idea]` | `gist` / `status` / `enabled_by` / `blocked_by` / `reviewed` |

- `credibility`: `peer-reviewed` / `preprint` / `primary` / `secondary` / `blog` / `generated`
  から選ぶ。`generated` は LLM がこの wiki のために生成した調査結果で、扱いが他と違う（§12）。
- `confidence`: `high` / `medium` / `low` / `open` の 4 段階。
- `status`: `open` / `done` / `dropped` の 3 つ。**進捗は表さない**（§8）。
- `reviewed` は **確信度（thesis）や状態（idea）を見直した日**であり、
  Cosense が自動で付ける `Updated` 列とは別物。
  誤字修正でも `Updated` は更新されてしまうため、陳腐化の検出には使えない（§13 lint）。
- **source ページ（`#raw` / `#bookmark`）に Infobox を持たせない。** `ingested` / `url` は summary 側と重複し、
  持たせても下記の制約でノイズが増えるだけである。
- `raw` は対応する source ページ（`📄` または `🔖`）へのリンク。bookmark の summary を直接書く場合（`🔖` タイトルで型が `[summary]`）は `raw` を省略し、`url` で URL を保持する。対応する source ページが別に無いので、自身へのリンクは書かない。

### 抽出指示（2 列目）

`table:infobox` の各行は `<キー>\t<抽出指示>` の 2 列で書く。1 列目がキー、
**2 列目はそのキーをどう抜き出すかを LLM に与える指示**である。
2 列目は表示に使われないため、表の見た目は変えずに抽出の挙動だけを変えられる
（/villagepump/infobox の検証記録で確認。Web UI は 1 列目だけを表示する）。

- **すべてのキーに「書かれていなければ空欄とせよ」を書く。**
  下の制約 2 の捏造に対して、こちらから打てる唯一の手である。
  ただし抽出が LLM ベースであることは変わらないので、保証にはならない。
  「信用してよいのは型定義ページの表だけ」は緩められない。
- **値が閉じた集合のキーは候補を列挙し、言い換えを禁じる。**
  `credibility` / `confidence` / `status` が該当する。
- **日付のキーは書式を書く。** `ingested` / `reviewed` は `YYYY-MM-DD`、
  `published` は `YYYY-MM` も許す。
- **リンクを取るキーは、何へのリンクに限るかを書く。**
  `raw` / `supported_by` / `refuted_by` / `enabled_by` / `blocked_by` が該当する。
  本文の他のリンクを拾わせない。
- **拾わせたくないものは名指しで除く。**「〜へのリンクだけを抜き出せ」では足りない。
  実測: `raw` に「`📄` または `🔖` で始まる source ページへのリンク」とだけ書いたところ、
  対応する source ページを持たない bookmark summary が**自分のタイトル**を値にした（§7）。
- **空欄の指示は `null` を名指しで禁じる。**
  実測: 「空欄とせよ」だけでは、値が `null` と書かれた行が残った。

**実際の文面は各プロジェクトの型定義ページが持つ。`AGENTS.md` には写さない。**
二重に持つと必ず食い違う。
**指示を書き換えると、その型にリンクしている全ページの抽出が走り直す。**
値の揺れが実害を出していないなら触らない。
反映は遅く、かつ全行には及ばない（2026-08-20 実測: 1 回目の書き換えは 4 分後で古いまま、
1 時間後に入れ替わった。2 回目は 39 行中 20 行だけが入れ替わり、その後 70 分は 1 セルも
動かなかった）。**書き換え直後の表を検証に使わず、古い指示で付いた値が残る行があると考える。**
**残った行はページを読むだけでは直らない。** 実測: 古い値が残った 7 行を `browsePage` で
閲覧しても、80 分後まで 1 セルも変わらなかった。

### 制約（2026-08-05 に実地検証）

Cosense の Infobox 抽出は **LLM ベース**であり、構文的な転記ではない。
`browsePage` のヘルプにも "hallucination または truncated と判定された Infobox は除外する"
とある通り、抽出結果は常に正しいとは限らない。

1. **反映に 1 分程度のラグがある。** ページ作成直後は行が現れても値が全て空になる。
   ingest 直後の確認は一呼吸おく。
2. **`table:infobox` を書いたページは、それ自体が定義ページになる。**
   そのページにリンクしている全ページが表の行として並び、
   **列に対応する記述が無くても値が捏造される。**
   実測: Infobox を持たない source ページに、本文に存在しない `gist` `kind` `raw` が生成された。
3. **その結果、`summary` / `thesis` にリンクしただけのページが索引を汚す。**
   実測: 説明文中でリンクしていた型定義ページ 5 枚が、偽の `gist` `raw` `url` を持つ 5 行として並んだ。
   §4 の「instance 以外からリンクしない」と外部 URL 記法はこれへの対処であり、
   型定義ページ 9 枚の状態で両方の表を 0 行に戻せることを確認済み。

4. **リンク記法の角括弧が落ちることがある。**
   実測: 本文に `[Anthropic]` と書かれた `author` が、表では `Anthropic` になった行が 6 つあった。
   表の値をそのまま本文へ貼らない。リンクが要るときはリンク元ページの本文を読む。

したがって **信用してよいのは型定義ページ（`summary` / `thesis`）の表だけ**である。
個々の summary / thesis ページに対して `browseRelatedPages` を使ってはならない（§9）。

## 6. source ページの規約

source を wiki と同じ名前空間に置くため、識別と扱いのルールを厳密に決める。source には `#raw` として本文を転記して保持する raw ページと、`🔖` として URL のみを保持する bookmark ページの 2 種類がある（§0）。

### 識別

- **raw ページのタイトルは `📄<原題>`。** 絵文字と原題の間に空白を入れない。
  空白は URL 上で `_` に変換されるため、区切り位置にアンダースコアが戻ってしまう。
  例: summary `Attention Is All You Need` / raw `📄Attention Is All You Need`。
- **bookmark ページのタイトルは `🔖<URLのタイトル>`。** 同様に空白を入れない。例: `🔖Attention Is All You Need`。
  タイトルは URL のタイトルそのままを使い、日付等の付加はしない。仮置きの bookmark は `#bookmark` タグや保存日時を本文に持つことがある。summary を直接書く場合は `[summary]` 型で同じ `🔖` タイトルを使う（§2）。
- **本文 1 行目は `#raw`、`#bookmark` または `[summary]`。** raw ページは `#raw`、URLのみの仮置きは `#bookmark`、要約を伴う bookmark は `[summary]`。raw の 2 行目は対応する `[summary]` ページへのリンク、仮置き bookmark の 2 行目も対応する `[summary]` へのリンク（未作成なら空リンク）。bookmark summary は自身が `[summary]` なので、2 行目に `#bookmark` タグを置き、続けて Infobox と `takeaways` 等の summary 節を書く（例は §7 構成）。**そのソース自身の URL は Infobox の `url` だけに持たせ、本文に裸の URL 行を置かない**（§5）。
  他のソースを指す URL は summary の `references` に置く（§7）。保存日時は Infobox の `ingested` が兼ねる。**Infobox は `#raw` / `#bookmark` ページには書かない**（§5）。出典のメタデータは summary 側が持つ。
- **どのページが source 層かは、次の 1 つの判定で決める。** タイトルが `📄` で始まる、
  または本文 1 行目が `#bookmark`。このどちらかに当たるページが source 層で、残りは wiki 層である。
  **`🔖` タイトルでも本文 1 行目が `[summary]` の bookmark summary は wiki 層**である。
  §9 の検索、§10 の矛盾検出、§13 の lint で「source を除く」と書いてあるのは、すべてこの判定を指す。
  判定をここ 1 箇所に置くのは、印を増やしたときに検査側が取り残されるのを防ぐためである
  （bookmark 導入時に実際に起きた）。
- 極端に長い原文は章単位で分割する。連番は末尾に付ける。例: `📄<原題> (1/3)`。
  上限を超えると `previewEdit` が `request entity too large` で 400 を返す。
- **上限は文字数ではなく、バイト数と行数の組み合わせで決まる**（2026-08-08 に実測）。
  日本語は 1 文字 3 バイトなので、和文だけを見ていると「およそ 15,000 文字」に見えるが、
  **英語の原文なら 5 万文字を超えても 1 ページに入る。**
  実測値: 57,000 バイト / 600 行は通る。60,298 バイト / 599 行と 49,506 バイト / 901 行はどちらも 400。
  バイトと行のどちらか一方だけを見ても判定できないので、目安は **55,000 バイトかつ 600 行**に置く。
  **`previewEdit` は dry-run なので、迷ったら実際に投げて確かめる。** ページは作られない。
  分割数を減らすと、1 ページに文脈がまとまり、query のときに読む枚数も減る。
  空行の連続を畳み、段落の区切りを見出しの前だけに寄せると行数を半分近くまで落とせる。
- **分割は必ず文書順を保つ。** サイズを揃えるために章を詰め替えてはならない。
  §6「段落の並べ替えはしない」に反する。各ページの分量が不揃いになる方を選ぶ。
  節が単独で上限を超えるときだけ、その節の中を段落境界で切る。切った旨は summary の `caveats` に書く。

### 改変の範囲

- **元の意味を変えない範囲での修正はしてよい。**
  明らかな誤字脱字、取り込み時に壊れた改行、文字化けは直す。
- **要約・省略・言い換え・段落の並べ替えはしない。** 原本として引用の裏取りに使えることが価値である。
- 判断に迷う修正（原著者の誤りかもしれないもの）は直さず、
  `[summary]` ページ側の `caveats` に「原文では〜となっているが〜と思われる」と書く。

### リンク

- **本文中の固有名詞・概念には積極的にリンクを張る。**
  これにより、concept ページの被リンクを見れば **「どの原文から生成されたページか」** が辿れる。
  summary に落ちなかった言及も、原文からのリンクとして残る。
- ただし **その原文が実際に論じている対象に限る。**
  語が 1 度出てきただけでリンクすると、concept ページの被リンクが原文で埋まり、
  リンクグラフが「そこから辿りたいもの」を指さなくなる。
- 画像そのものがソースで本文テキストが無い場合は、リンクを埋め込む先が無いので、
  参照行の下に `mentions: [X] [Y] [Z]` の形でリンク行を置く。
- **後からリンクを付けるときは機械的に検証する。** ブラケットを挿入したあと、
  角括弧を除去した文字列が編集前と一致することを確認してから submit する。
  意図しない本文改変（§6 改変の範囲）を確実に防げる。

### ファイル

**ファイルは一切アップロードしない。** PDF・画像・記事中の挿図、いずれも URL 参照にする。
`cosense` CLI にアップロードコマンドが無く、アップロードすると必ず人間の手作業が挟まるため。

そのうえで、**テキストは必ず原文ページに転記する。**
PDF の論文なら本文テキストを抽出して置く。HTML 記事と扱いは同じで、
`📄` ページが「引用の裏取りができる原本」であるという役割はここで担保される。

ファイル本体は URL で参照する。

- PDF・元ファイル: `source: <url>`
- 画像・挿図: `(image) <alt またはキャプション>` の次の行に **`[<画像URL>]`**。
  **ブラケットで囲んだ URL を Cosense は画像として埋め込み表示する。**
  ページリンクにはならないのでリンクグラフを汚さない。

**画像は拡張子で終わる URL を使い、クエリパラメータは落とす。**
クエリの中に拡張子がある CDN のリサイズエンドポイントは画像と認識されない。
直し方は `docs/convert-html.md` の「画像 URL の扱い」にある。

### URL 参照の代償

これは原著からの意識的な逸脱である。原著は "URLs that may break" を理由に画像をローカルへ
落とすことを勧めており、実際 **元 URL が切れれば図・レイアウト・表組みは失われる。**
クエリパラメータを含む URL は特に切れやすい。
失われないのは原文ページに転記したテキストだけである。したがって:

- **図・表が伝えている内容のうち重要なものは summary の `takeaways` に言葉で書く。**
  図に依存した理解を URL だけに預けない。これが逸脱に対する唯一の防御になる。
- PDF は取り込み時に一度だけ取得できればよい。テキストさえ抜き出して置けば、
  以後の query で元 URL に依存しない。

### HTML 記事からの変換

**`fetch-proxy`（https://github.com/mpppk/fetch-proxy）で取得してから Cosense 記法に写す。**
手順は `docs/convert-html.md` に置く。HTML 記事を ingest するときはそれを読む。

変換で落ちるもの（タイトルの短縮、引用の組織名、著者名、`<iframe>` のままの埋め込み）と、
貼る前に必要な点検（`[` `]` とバッククォートの衝突、コードブロック内のエスケープ）が
そこにまとまっている。**点検を飛ばすと空リンクが大量に生成される**ので必ず読む。

## 7. summary ページの規約

`[summary]` は 1 ソース 1 枚。**原文の圧縮ではなく、リンクグラフへの接続点**である。
原文が同じ名前空間にあっていつでも降りられるので、詳細を保存する義務はない。

役割は 2 つ:

1. query 時に **原文を読まずに「このソースが何を言っていたか」を思い出す**
2. concept ページから **「どのソースがこれを論じたか」を辿る入口**

### 構成

raw を持つ場合。

```
[summary]

table:infobox
 gist	[再帰]を使わず[Attention]だけで系列変換ができ、しかも速い
 kind	論文
 author	[Ashish Vaswani]
 published	2017-06
 ingested	2026-08-05
 raw	[📄Attention Is All You Need]
 url	https://arxiv.org/abs/1706.03762
 credibility	peer-reviewed

takeaways
 [RNN]の逐次計算が並列化を阻んでいる
  [Transformer]は[Self-Attention]のみで構成し、系列長に対して並列に計算できる
 [Multi-Head Attention]で異なる表現部分空間を同時に見る
 [Positional Encoding]で順序情報を与える
  再帰を捨てた代償で位置情報が失われるため

quotes
 "We propose a new simple network architecture, the Transformer, based solely on attention mechanisms, dispensing with recurrence and convolutions entirely."

caveats
 実験は[機械翻訳]のみ。他タスクへの一般化は本論文では示されていない

references
 [Neural Machine Translation by Jointly Learning to Align and Translate https://arxiv.org/abs/1409.0473]
  原文が[Attention]の初出として挙げている
 [Layer Normalization https://arxiv.org/abs/1607.06450]
  残差接続の後段で使われる。実装まで追うなら次はここ
```

**bookmark summary**（`🔖` タイトルで型が `[summary]`。§6 識別）は、対応する source ページが
別に無いぶんだけ違う。節の書き方と分量は同じなので、差分だけ示す。

```
[summary]
#bookmark

table:infobox
 gist	（同じ）
 kind	ブログ記事
 ingested	2026-08-14
 url	https://example.com/blog/mcp-authorization
 credibility	blog

takeaways
 （同じ）
```

- **`raw` を書かない。** 降りる先の source ページが無い（§5）。
- **`url` がそのソース自身の URL の置き場所である。** 本文に裸の URL 行を置かない。
  二重に持つと必ず食い違う。他のソースを指す URL は `references` に置く（下記）。
- **`#bookmark` は 2 行目に置く。** source 層の判定は**本文 1 行目**だけを見るので、
  1 行目が `[summary]` であるこのページは wiki 層のままである（§6 識別）。
  このタグは「bookmark から起こした summary である」という由来の記録であって、層の印ではない。
- 保存日時は `ingested` が兼ねる。別に日付行を持たない。

### 各節の役割

- **`gist`（Infobox）** — このソースの主張を 1 行で書く。Infobox に置くことで
  `browseRelatedPages .../summary` の表に列として現れ、**全 summary の一覧が
  「リンク + 1 行要約 + メタデータ」の表**になる。karpathy の index.md はここで再現される。
- **`takeaways`** — **自分の言葉で書く。** 原文の言い回しを写しても原文ページと重複するだけで
  情報が増えず、リンクを埋め込む余地もなくなる。固有名詞・概念は `[ ]` で囲む。
  根拠・補足はインデントでぶら下げる。原著の "key takeaways" に対応する。
- **`quotes`** — 原文ママ。**回答に貼る可能性がある箇所だけ**、3〜5 個まで。
  毎回原文ページから探し直すとコンテキストを浪費するため、ここに置いておく。
- **`caveats`** — そのソースの限界。検証範囲・時点・サンプル・利益相反。
  リサーチでは「**何が言えないか**」が `[thesis]` の `confidence` を決める。
- **`references`** — そのソースの**外側**にある URL を集める。入るものは 3 種類:
  ①原文が挙げている重要な参照先（引用文献・仕様・PDF）、②この summary を書くために自分が辿った URL、
  ③深掘りするときに次に読むべき URL。**次の ingest の候補リスト**であり、
  空リンクが「次に書くべきページ」のキューであるのと同じ役割を、まだ wiki に無い URL に対して果たす（§4）。

### references の書き方

- **必ずラベルを付けて `[<ラベル> <URL>]` と書く。** ブラケットの中が URL だけの行は
  Cosense が画像として埋め込もうとする（§6 ファイル）。ラベルは原題・仕様名にする。
- **外部リンク記法はリンクグラフに乗らない**（§4）。何件書いても被リンクと Infobox は汚れない。
- **既に wiki にあるソースは、URL ではなくページリンク `[<summary のタイトル>]` で書く。**
  URL はその summary の Infobox `url` が持っているので、重ねて持つと必ず食い違う。
  ページリンクはリンクグラフに乗るため、ソース間の参照関係がそのまま辿れるようになる。
- **そのソース自身の URL は書かない。** Infobox の `url` の役目である（§7 bookmark summary）。
- 子行に一言添え、**原文が挙げていたものか、自分の探索で辿ったものかが分かるように書く。**
  後者は原文の裏取りにならないので、区別が要る。
- 5 件程度、多くても 10 件まで。**原文の参考文献一覧を丸写ししない。**
  全部は原文ページにあるので、ここには**また辿る可能性があるものだけ**を残す。
- `credibility` が `generated` な調査結果ページの summary では、
  本文中の一次資料のうち重要なものをここに上げる。
  §12 の「次に読むべき一次資料の索引」がこの節で具体化する。
- **Infobox のキーにはしない。** 値が複数行になるうえ、Infobox の抽出は LLM ベースで
  転記が保証されない（§5）。`takeaways` と同じく節として持つ。

### 分量

**原文の長さに比例させない。** 50 ページの論文もブログ記事も、summary の分量は同程度でよい。
目的は圧縮ではなく再利用であり、**原文に降りるかどうかを判断できる粒度**があれば足りる。

### 書かないこと

- 原文の章立てをなぞった逐次要約（原文ページを読めばよい）
- 支持／反証する `[thesis]` の列挙。極性は `[thesis]` 側の `supported_by` / `refuted_by` に
  一元化する。そちらから張られたリンクが summary の被リンクに出るので、
  両方に書くと必ず食い違う。
- 実現を助ける／阻む `[idea]` の列挙。同じ理由で `[idea]` 側の
  `enabled_by` / `blocked_by` に一元化する（§8）。
- 原文の参考文献一覧の丸写し（`references` は次に読むものだけ。全部は原文ページにある）
- 「関連ページ」節（§4）

## 8. idea ページの規約

`[idea]` は **ユーザーが実現したいこと**を 1 ページに 1 つ持つ。原著にない新設の型で、
wiki の中で唯一「読んだもの」ではなく「作りたいもの」を指す。

役割は 2 つ。

1. 実現したいことを wiki の文脈に置き、**ingest のたびに材料と障害が集まる**入口にする
2. まだ書かれていない concept と、まだ立てられていない question を空リンクとして溜める

**作るのはユーザーが指示したときだけである。** LLM が「こういうものが作れそう」と考えて
立ててはならない。`[idea]` はユーザーの意志の記録であり、LLM が推測で埋める型ではない（§0）。
書いた記録は日付ページに 1 行残す。動詞はその作業が生じた操作のもので、増やさない（§11）。

### 構成

```
[idea]

table:infobox
 gist	一次対応を[エージェント]に任せ、人間は例外だけを見る運用にしたい
 status	open
 enabled_by	[<summary のタイトル>]
 blocked_by	[<summary のタイトル>]
 reviewed	2026-08-17

何を実現したいのかを散文で書く。固有名詞・概念は[ ]で囲む。

motivation
 なぜ実現したいか

approach
 現時点でどう実現するかの当たり
  根拠や補足はインデントでぶら下げる

open_questions
 [<question のタイトル>]
 まだページの無い問いは空リンクで置く
```

### 各節の役割

- **`gist`（Infobox）** — 実現したいことを 1 行で書く。`browseRelatedPages <projectUrl>/idea` の
  表に列として現れ、**全 idea の一覧が「リンク + 1 行 + 状態 + 根拠」の表**になる。
  ingest のたびに関係するアイデアを探す操作は、この表を見ることである（§13 手順 8）。
- **`status`（Infobox）** — `open` / `done` / `dropped` から選ぶ。
  **表すのは「まだ生きているか」だけで、進捗は追わない。**
  検討中と着手中を分ける値を置くと wiki がタスク管理に寄り、
  誰も更新しない状態欄が増える。lint が見直すべきアイデアを絞るための最小限である。
- **`enabled_by` / `blocked_by`（Infobox）** — 実現を助ける／阻む summary へのリンク。
  `[thesis]` の `supported_by` / `refuted_by` と同じ構造で、同じ理由により **idea 側に一元化する。**
  極性は被リンクでは表現できないので、この手書きの列挙が
  「関連ページ節を手書きしない」（§4）の例外になる。**summary 側には書かない**（§7）。
- **`reviewed`（Infobox）** — このアイデアを最後に見直した日。`Updated` とは別物である（§5）。
- **`motivation`** — なぜ実現したいか。**ユーザーの言葉が元にあるならそれを保つ。**
  動機は後から復元できず、失われたアイデアは「やる理由の分からない TODO」になる。
- **`approach`** — 現時点でどう実現するかの当たり。**確定した設計ではない。**
  ingest で材料が増えたら書き換わってよい。実現可能性の主張はここに書かず、
  `[thesis]` に切り出してリンクする（§2 型の使い分け）。
- **`open_questions`** — 実現する前に決着が要る論点。`[question]` へのリンク、
  またはまだ無い問いの空リンクを置く。lint の「次に立てるべき問い」がここに溜まる。

### `generated` なソースの扱い

**`credibility` が `generated` のソースを `enabled_by` / `blocked_by` に入れてよい。**
`[thesis]` では禁じているが（§12）、あれは LLM の出力を根拠に `confidence` が上がるのを防ぐ規則である。
`[idea]` は真偽を問う型ではなく、`enabled_by` は確信度を上げる操作ではない。
調査結果ページは実現の材料そのものなので、ここでは素直に根拠として使う。

### 孤立させない

`[idea]` が張るのは summary への外向きリンクだけなので、そのままでは被リンク 0 になる。
`[thesis]` と同じく、**関係する `[concept]` から 1 本リンクを張る**（§4）。

### 書かないこと

- 進捗・期限・担当（タスク管理ではない。`status` の 3 値で足りる）
- 実現可能性の主張（真偽を問えるので `[thesis]` に切り出す。§2）
- 「関連ページ」節（§4）

## 9. 検索の順序

source が同じ名前空間にあるため、検索結果は wiki 層と source（`📄` / `🔖`）が混ざる。以下の順で降りる。

1. `cosense searchVector <projectUrl> <query>` — 意味の近いページを探す。
   `exists: false` は未作成ページ（空リンク）なので、書くべきページの発見にも使う。
   **これは意味検索であり、完全一致の存在確認には使えない。**
   `SEP-2322` を問い合わせても top-1 が `SEP-2567` になる（2026-08-05 実測）。
   識別子のように文字列が似ていて意味が近いページ群では特に区別できない。
   特定タイトルが存在するかは `readPage` でページ本文を読んで確かめる。
2. `cosense searchFullText <projectUrl> <query>` — 語句が確定しているとき。
   **source 層のページ（§6 識別）は、この段階では読み飛ばす。**
3. `cosense browsePage <pageUrl>` で本体を読む。
4. `cosense list1hopLinks` / `search1hopLinks` / `search2hopLinks` で周辺を辿る。
   単独ページでは見えない文脈がここで浮かぶ。
   **本文の無いページ（空リンク）は `list1hopLinks` に現れない。**
   リンクグラフ上は繋がっており、ページからクリックでは辿れる。
   空リンクを張ったかどうかの確認は、リンク元ページの本文を読む。
   **concept ページの被リンクには source ページが混ざる。** これは「この概念に言及している source」の
   一覧であり、ソースを横断して裏取りしたいときに使う。
   **`browseRelatedPages` は型定義ページ（`summary` / `thesis`）にのみ使う。**
   Infobox を持つページに使うと、先頭に捏造値を含む表が出る（§5）。
   個々の summary / thesis の周辺を見るときは `list1hopLinks` を使う。
5. **引用の裏取りや、summary に落ちた情報を拾う必要があるときだけ原文ページに降りる。**

source ページを常に読むと、その分だけ確実にコンテキストを浪費する。既定では降りない。

## 10. 矛盾と鮮度

- 新しい情報が既存の記述と食い違ったら、**古い記述を消さない。**
  該当行の直下にインデントして `⚠ [<summary のタイトル>] では〜としており矛盾` と書く。
- 矛盾が解決したら、解決の根拠を書いた上で整理する。
- `cosense searchFullText <projectUrl> '⚠'` で未解決の矛盾を一覧できる。
  **結果から source 層のページを除く（§6 識別）。** 矛盾の注記は wiki 層にしか書かないので、
  source に出る `⚠` は原文が元から持っていた記号である（§6 改変の範囲）。
  この検索は `⚠️`（異体字セレクタ `U+FE0F` 付き）にも当たる。Cosense の全文検索は空白を
  区切りとして扱うため、`'⚠ '` のように末尾へ空白を足しても絞り込めない（2026-08-06 実地検証）。
  同じ理由で、summary の `quotes` に `⚠️` を含む引用があると偽陽性になる。
  原文ママの原則（§7）を優先し、その行は偽陽性として読み飛ばす。
- 時点依存の記述には必ず「いつ時点の情報か」を書く。
- 矛盾を見つけたら、対応する `[thesis]` の `confidence` と `reviewed` を更新する。

## 11. ログ

- 日付ページ（`2026/08/05` 形式）に 1 行ずつ append する。単一のログページは作らない。
- 各行は動詞で始める: `ingest [<summary のタイトル>]` / `query <要旨>` / `lint <要旨>`。
  動詞は原著の 3 操作（§13）と同じ語を使う。**動詞を増やさない。**
- `[synthesis]` `[question]` `[idea]` を書いた記録は、**どの操作の中で生じたか**で動詞が決まる。
  取り込みの過程で既存の synthesis を更新したなら `ingest`、
  問われて比較や分析を書いたなら `query`。原著も synthesis を両方の操作に置いている。
  アイデアを書き留めるよう指示された場合も、新しい動詞は作らず `query` で記録する。
- 日付ページの 1 行目は `[log]`。
- 時系列は `cosense listPages <projectUrl> --sort created` で辿れる。

## 12. ユーザーからの指示

ユーザーは wiki 上に直接、指示やコメントを書ける。チャットの外に置くことで、
**問いがページの文脈に付いたまま残る**。エージェントはこれを発見して操作を実行する。

### 記法

Cosense の慣習に従い、**人間は自分の発言の行末にアイコンを置く。**

```
[query] MCP の認可、2026 以降の動きを調べて [yuki.icon]

ここは後で読み直したい [yuki.icon]
```

規則は 3 つ。

- **行末が `[yuki.icon]` の行は人間の発言。** それ以外の行はすべて LLM が書いた wiki 本文である
  （§0）。したがって **LLM は自分の発言に署名しない。** 無署名であること自体が署名になる。
- **行頭に操作名のリンクがあれば指示、無ければコメント。**
  マーカーは §13 の操作名をそのまま使う ── `[ingest]` / `[query]` / `[lint]`。
  どれか迷ったら `[query]` にする。
  **コメントには何もしない。** 読んで文脈として使うだけで、ページを書き換えない。
- **マーカーとアイコンは同じ行に置く。** 長い指示は下にインデントでぶら下げる。
  子行に署名は要らない。親行のアイコンが指示全体を覆う。

既定が「何もしない」側なので、ユーザーが独り言を書いても誤って走り出すことがない。

### チャットでの省略記法

チャットには被リンクのキューが無いので、マーカーは要らない。代わりに 1 つだけ約束がある。

**ユーザーが URL だけを貼ったら、それは ingest の依頼である。** そのページを取り込み、
§13 ingest の手順を実行する。何も添えられていなくても、貼る行為そのものが指示なので
「取り込みますか」と聞き返さない（§0 の「明示的に指示した時のみ」を満たす）。

- 文が添えられていればそちらが優先する。「これ読んで意見だけ聞かせて」なら取り込まない。
- **wiki 上ではこの省略は効かない。** URL だけの行はコメントのままで、指示にするには
  行頭のマーカーが要る。ページ本文には参照として URL を書くことがあり、
  既定を「何もしない」側に保つ必要があるため。

### 発見と完了

未処理の指示は**マーカーの被リンク**で引く。手書きの inbox ページは作らない（§4）。

```
cosense list1hopLinks https://scrapbox.io/<project>/query
```

このため `[ingest]` `[query]` `[lint]` の 3 ページは実体を持たせる。本文は操作の説明と、
被リンクが未処理の指示のキューである旨。`table:infobox` は書かない（§5）。
**キューが空のとき被リンク 0 になるのが正常**なので、lint の孤立ページ検査からは除く（§13）。

**操作ページには、キュー以外のリンクを出入りとも持たせない。**
`list1hopLinks` は外向きリンクと被リンクを 1 つの一覧にまとめて返すため、どちらが増えても
キューにノイズが乗る。守ることは 2 つ。

- **指示行以外から操作ページへリンクしない。** 規約や入口ページでの例示も含む。
  クリックで辿れるようにしたいときは外部 URL 記法を使う（§4）。
- **操作ページの本文にリンク記法を書かない。** 型や概念に触れるときは平文で書く。

処理し終えたら、指示行の形に応じて 2 通りの処理をする。

1. **指示に追加情報が無い場合は、その行を削除する。** 回答も記載しない。
   `[ingest][yuki.icon]` とだけ書かれた行がこれに当たる。
2. **指示に追加情報がある場合は、マーカーのリンクだけを削除し、文言は残す。**
   続けて、インデントした子行として回答を記載する。

```
[ingest]このページで参照しているAAAについても記載 [yuki.icon]
 [AAA] ページを作成しました
```

処理後は次のようになる。

```
このページで参照しているAAAについても記載 [yuki.icon]
 [AAA] ページを作成しました
```

**ユーザーの行を書き換えるのは、マーカーリンクの削除と、追加情報の無い指示行の行削除だけである。**
文言の修正・要約はしない。

### アイコン記法の性質（2026-08-06 に実地検証）

**`[X.icon]` はリンクグラフに一切乗らない。** ページ JSON では `links` とは別の `icons` 配列に
入り、`relatedPages.links1hop` にも現れない。実測: villagepump の `takker` はアイコンとして
多用されているが `linked` は 14 で、`[takker.icon]` を含む `井戸端` は `links1hop` に現れない。

ここから 2 つが従う。

- **署名はただである。** §5 の Infobox 捏造行も、§13 lint の「育ちすぎたハブ」も起こさない。
  `yuki` はプロジェクトメンバーなので、ページが無くてもアイコンは表示される。
- **アイコンだけではキューを作れない。** 指示の検出にリンク記法のマーカーが要るのはこのためである。

発言の検出には次の 2 つが使える。

- `browsePage` の「人間のアイコン記法」節は、**プロジェクトメンバー名に一致するアイコンだけ**を
  列挙する。ページを 1 枚読めば人間の発言の有無が分かる。
- `cosense searchFullText <projectUrl> 'yuki.icon'` で発言のあるページを横断的に引ける。
  `.icon` まで含めて一致する（実測: `Mijikko.icon` は 100 件、`Mijikko.zzz` は 0 件）。
  マーカーの付け忘れを拾うのに使う。**拾っても勝手に実行はせず、次の会話で確認する。**

**`[yuki]` はアイコンを置くためだけのプロフィールページであり、wiki の内容ではない。**
型を持たず、被リンクも持たない。ingest / query / lint のいずれの対象にもせず、
§13 lint の孤立ページ検査からも除く。Cosense の雛形のまま `#member` 等を含むが、
人間の持ち物なので §4 のハッシュタグ規約もここには及ばない。
`yuki.icon` の全文検索がこのページに当たるのも、同じ理由で無視してよい。

### 調査結果ページ

指示に答えるのに外部調査が要った場合、**その結果を source として保存する**（§6）。
チャットに流して捨てない。以後の query は wiki の中だけで完結する。

- タイトルは `📄<調査内容を表す名詞句>`、1 行目 `#raw`、2 行目は対応する `[summary]` へのリンク。
  §6 の source ページと同じ扱いになり、§9 の検索でも同じように読み飛ばされる。
- **参照した URL は本文に必ず残す。** これが唯一の裏取り経路になる。
- 作ったあとは §13 ingest の手順 3 以降をそのまま適用する。
- summary の `credibility` は `generated`、`kind` は `調査結果`。
  元 URL も著者もないので `url` と `author` は書かない。
  `caveats` に「LLM が生成した調査結果。一次資料は本文中の URL」と書く。
- 依頼元の行から結果ページへリンクが張られるので、孤立ページにはならない（§4）。

**`generated` なソースを `[thesis]` の `supported_by` / `refuted_by` に入れてはならない。**
LLM の出力を LLM が要約して確信度の根拠にすると、新しい証拠が 1 つも増えないまま
`confidence` だけが上がる。生成レポートは **次に読むべき一次資料の索引**として使い、
そこで挙がった一次資料を別途 ingest したものだけが thesis の根拠になる。

## 13. 操作

操作名は原著のまま `ingest` / `query` / `lint` の 3 つ。

### ingest（ソースの取り込み）

1. source ページを作る。全文を保持するなら raw、URL だけでよいなら仮置きの bookmark、
   URL と要約を同時に書くなら bookmark summary。タイトルと本文の作りは §6 識別に従う。
   PDF もテキストを抽出して raw に置き、ファイル自体は URL で参照する（§6 ファイル）。
2. source（raw の本文または bookmark の URL 先）を読み、takeaways をユーザーと会話して確認する。
3. summary ページを §7 の構成で作る。raw の場合は `[<原題>]` を新規に作り、
   bookmark summary の場合は手順 1 で作ったページがそれに当たる。**本文中の固有名詞・概念はリンクにする。**
   読む過程で出てきた参照先 URL は、その場で `references` に残す（§7）。後から原文を読み直すことになる。
4. source ページに戻り、その source が実際に論じている concept / person / organization に
   リンクを張る（§6）。bookmark summary の場合は自身の `takeaways` 内のリンクで兼ねる。
5. 出てきた `[concept]` `[person]` `[organization]` ページを新規作成、または既存ページに追記する。
6. 関係する `[thesis]` の `supported_by` / `refuted_by` / `confidence` / `reviewed` を更新する。
   新しいテーゼが立つなら `[thesis]` ページを新規作成し、
   **関係する `[concept]` ページから 1 本リンクを張る。**
   thesis からは summary へ張るだけなので、そのままでは被リンク 0 の孤立ページになる（§4）。
7. 関係する `[synthesis]` を更新する。原著が ingest の説明で
   "strengthening or challenging the evolving synthesis" と書いている部分がこれに当たる。
   **同じ主題の 2 本目が揃った時点で `[synthesis]` を新規に立てられないか検討する。**
   thesis と同じく孤立しやすいので、関係する `[concept]` から 1 本リンクを張る。
8. 関係する `[idea]` を更新する。`cosense browseRelatedPages <projectUrl>/idea` の表で
   `gist` を見比べ、その source が実現を助けるなら `enabled_by`、阻むなら `blocked_by` に足し、
   `reviewed` を更新する。材料が増えたなら `approach` と `open_questions` も書き換える。
   **`status` が `done` / `dropped` のものは触らない。**
   **新しいアイデアをここで立てない**（§8）。ユーザーの指示なしに増える型ではない。
9. 日付ページに 1 行追記する。
10. wiki 上の指示から始まった取り込みなら、依頼行に結果を返して指示行を片付ける。
    `[ingest]` と URL しか無い依頼行は、結果リンクを繰り上げて行ごと消す（§12）。

1 ソースの取り込みで 10 ページ前後に触ることになる。それが正常である。

### query（質問への回答）

1. §9 の順序で検索・読解する。
2. wiki の中で答えが出ないときは外部を調べ、**結果を調査結果ページとして wiki に戻す**（§12）。
3. summary ページへのリンクを示しながら回答する。
4. **回答に再利用価値があれば `[question]` ページとして wiki に戻す。**
   探索の成果をチャット履歴に捨てない。これが wiki を複利で育てる部分である。
5. wiki 上の指示に答えた場合は、依頼行に結果を返してマーカーを削除する（§12）。

### lint（健全性チェック）

Cosense では機械的に検出できる。定期的に実行する。
検査項目とコマンドは `docs/lint.md` に置く。lint を回すときはそれを読む。

各検査は `projects/` 下で定義されたプロジェクトごとに実行する（`<projectUrl>` は `https://scrapbox.io/niki-auth` / `https://scrapbox.io/niki-ai` / `https://scrapbox.io/niki-cs` / `https://scrapbox.io/niki-tech`）。

lint では検出だけでなく、**次に読むべきソースと、次に立てるべき問いを提案する。**

## 14. やらないこと

- 構造語の和訳・言い換え（`summary` を `出典` と書かない。§0）
- 手書きの目次・index ページ（必ず腐る。被リンクと Infobox に任せる）
- 「関連ページ」節の手書き
- タイトルのプレフィックスによる疑似階層（source の `📄` / `🔖` のみ例外。§3）
- 原文の要約・省略・言い換え（誤字修正は可。§6）
- 原文からの無差別なリンク付与（論じている対象に限る。§6）
- `references` への参考文献一覧の丸写し、およびラベルの無い URL 行（§7）
- `#raw` / `#bookmark` 以外のハッシュタグ記法
- 巨大な 1 ページ（分割してリンクした方がグラフとして価値が出る）
- ユーザーの発言行の書き換え（マーカーリンクの削除と、追加情報の無い指示行の行削除のみ例外。§12）
- マーカーの無い発言を指示とみなして実行すること（§12）
- 指示行以外から操作ページへリンクすること、および操作ページ本文へのリンク記法（§12）
- `generated` なソースを thesis の `supported_by` / `refuted_by` に入れること（§12）
- LLM の判断で `[idea]` を立てること、および `[idea]` を進捗管理に使うこと（§8）

## 15. 編集の実行手順

Cosense へのページ作成・編集は `cosense previewEdit` で dry-run し、
内容を確認してから `cosense submitEdit` で確定する。
詳細は `cosense` スキルの `edit-page.md` に従う。

Cosense は追記の方がコストが低い。既存行の全面書き換えより、
行の追加とインデントによる構造化を優先する。
